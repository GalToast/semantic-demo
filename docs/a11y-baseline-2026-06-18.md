# A11y Baseline — 2026-06-18

## Purpose

Establish an automated accessibility (a11y) regression baseline for the 4 critical user-flow states in the semantic-explorer app. This baseline uses [axe-core](https://github.com/dequelabs/axe-core) via `@axe-core/playwright` to validate WCAG conformance and catch regressions early.

**Why a11y matters:**
- **Silent failures:** Unlike visual regressions (which show up in screenshots), a11y violations are invisible to sighted developers but block real users relying on screen readers, keyboard navigation, or high-contrast modes.
- **Real user impact:** ~15% of the global population lives with a disability. WCAG violations can prevent users from completing critical flows (searching, navigating, viewing results).
- **Legal compliance:** Section 508, ADA Title III, and EU Accessibility Act (2025) require WCAG 2.1 AA conformance for public-facing apps.

## Violation Categories to Watch

These 5 categories are the most common sources of WCAG violations in web apps and are the focus of this baseline:

### 1. `color-contrast`
- **WCAG criterion:** 1.4.3 Contrast (Minimum)
- **What it checks:** Text-to-background contrast ratio meets 4.5:1 (normal text) or 3:1 (large text)
- **Common causes:** Low-contrast placeholder text, disabled buttons, overlay text on images
- **Fix:** Adjust CSS color values or add `aria-label` to supplement visual-only text

### 2. `aria-*` (all aria-prefixed rules)
- **WCAG criterion:** 4.1.2 Name, Role, Value
- **What it checks:** ARIA attributes are valid, roles are used correctly, required properties are present
- **Common causes:** Missing `aria-expanded` on toggles, incorrect `role` values, orphaned `aria-labelledby`
- **Fix:** Add/fix ARIA attributes, ensure role semantics match behavior

### 3. `label` (form elements)
- **WCAG criterion:** 1.3.1 Info and Relationships
- **What it checks:** Form inputs have associated `<label>` elements or `aria-label`
- **Common causes:** Placeholder-only inputs, icon buttons without text labels
- **Fix:** Add `<label>` elements or `aria-label` attributes

### 4. `landmark` (region/landmark rules)
- **WCAG criterion:** 1.3.1 Info and Relationships
- **What it checks:** Page has proper landmark regions (banner, main, navigation, contentinfo)
- **Common causes:** Missing `<main>` element, no `<nav>` for navigation
- **Fix:** Wrap content in semantic HTML5 landmark elements

### 5. `heading-order`
- **WCAG criterion:** 1.3.1 Info and Relationships
- **What it checks:** Heading levels (h1–h6) are not skipped
- **Common causes:** Going from `<h1>` directly to `<h3>` without `<h2>`
- **Fix:** Ensure heading hierarchy is sequential

## How to Update the Baseline

### When a real a11y bug is fixed

1. Fix the bug in source code
2. Run `npm run test:a11y` — the violation count should **decrease**
3. Update the baseline table above with the new count
4. Commit the doc update with the fix

### When a new known issue is discovered

1. Run `npm run test:a11y` to capture the current counts
2. If a state exceeds the 5-violation threshold, either:
   - **Temporarily increase the threshold** by setting `A11Y_MAX_VIOLATIONS` env var:
     ```bash
     A11Y_MAX_VIOLATIONS=8 npm run test:a11y
     ```
   - **Or add a comment** in the baseline doc noting the known issue
3. Create a follow-up task to fix the violation

### When adding new UI components

1. Run `npm run test:a11y` to check if the new component introduces violations
2. If violations are found, fix them before merging
3. If the violations are pre-existing (not from the new component), update the baseline

## How to Interpret Failures

### Test passes (≤ 5 violations)
The app has no more than 5 a11y violations — within the baseline threshold. This is the expected steady state.

### Test fails (> 5 violations)
A regression has been introduced. The violation count increased beyond the threshold.

**Investigation steps:**
1. Check the console output for the specific violation rules
2. Run `npm run test:a11y` against the previous working commit to compare
3. Use axe-core's browser extension to inspect violations interactively
4. Fix the root cause (do not simply raise the threshold)

### Specific failure scenarios

| Scenario | Symptom | Action |
|----------|---------|--------|
| New color-contrast violations | Low-contrast text | Check CSS color values, especially in dark mode |
| New aria violations | Invalid ARIA attributes | Review dynamic ARIA updates in Svelte components |
| New label violations | Missing form labels | Add `aria-label` or `<label>` to form elements |
| New landmark violations | Missing regions | Add `<main>`, `<nav>`, `<header>` elements |
| New heading-order violations | Skipped heading levels | Fix heading hierarchy in the DOM |

## npm Script

```bash
# Run the a11y baseline test (4 states, ≤ 5 violations each):
npm run test:a11y

# Run with a custom violation threshold:
A11Y_MAX_VIOLATIONS=10 npm run test:a11y

# Run against the production preview:
TEST_BASE_URL=http://127.0.0.1:4174 npm run test:a11y
```

**Prerequisites:**
- A running dev server (`npm run dev:svelte`) or preview server (`npm run preview:svelte`)
- Playwright browsers installed (`npx playwright install chromium`)
- axe-core installed (`npm install --save-dev @axe-core/playwright`)

## Architecture

```
tests/integration/
├── a11y-baseline.spec.js              # 4-state a11y baseline test (this baseline)
├── w15-body-attr-live-probe.spec.js   # Integration probe (now includes a11y scans)
├── visual-state-snapshots.spec.js     # Visual regression (not modified)
├── helpers.js                         # Shared mock fetch + navigation helpers
└── __snapshots__/                     # Visual baseline PNGs

node_modules/@axe-core/playwright/     # axe-core Playwright integration
```

**Test execution flow:**
1. Navigate to app → install mock fetch routes → wait for scene readiness
2. Perform user actions (click search, type query, click result)
3. Run `AxeBuilder({ page }).analyze()` — injects axe-core into the page
4. Count violations, log details, compare against threshold
5. Pass if ≤ threshold, fail with descriptive error if > threshold
