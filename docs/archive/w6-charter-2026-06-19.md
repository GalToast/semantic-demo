## 2. The Three Architectural Paths

To reach **200 ms TBT** the page must fundamentally change how the first 2–4 seconds execute. There are three independent paths.

### Path A — SSR + CSR hydration

**Concept:** Server-renders the app shell (HTML + CSS + minimal JS) at request time. Client receives a fully painted page, then progressively hydrates Svelte components as they become visible.

**Implementation sketch:**

- Replace Vite SPA with `vite-plugin-ssr` or `astro`-driven build
- `App.svelte` mounts to a server-rendered shell with all body data-* attributes pre-set
- Three.js init happens **after hydration** in a separate chunk
- `initEngine()` becomes a lazy trigger, not eager

**Cost:**

- Phase 1: 2–3 weeks architecture work
- Phase 2: re-architect URL-state, parity-attrs, and bridge pattern (they were SPA-shaped)
- Phase 3: CI/test matrix doubles (SSR build + CSR build targets)

**TBT projection:** **15–80 ms** post-hydration (Three init happens after first paint). Lighthouse Perf score ≈ 90–95.

**Risk: HIGH.** Touches the engine kernel, lifecycle init, parity-attrs, url-state, navigation store. Most invasive W-prefix in the project's migration history.

### Path B — Lazy-shell behind user gesture

**Concept:** Render a CSS-only splash screen first. The full engine initializes **only after the user moves the mouse, presses a key, or scrolls**. Worker computes mycelium data while user reads the splash.

**Implementation sketch:**

- Replace `#semantic-explorer` initial paint with a static `<canvas>` placeholder CSS (gradient + ghost node icons)
- Hide `<Canvas />` Svelte component until user-gesture event fires
- `initData()` continues to run in worker during splash (already mostly happens in W44 work)
- Convert `initEngine()` to worker-driven Three init (off-main-thread)

**Cost:**

- Phase 1: 3–5 days UI + splash component + gesture monitor
- Phase 2: rework `requestIdleCallback` flow to coordinate with gesture signal
- Phase 3: Worker port for Three.js init (Three can't actually run in worker, but geometry data can)

**TBT projection:** **50–150 ms** for user-after-load (gesture → 3D ready). Lighthouse Perf score ≈ 80–88 once user interacts.

**Risk: MEDIUM.** Touches splash screen UI, Canvas mounting, lifecycle. Doesn't touch engine kernel. Bridges survive intact.

**Note:** This is the W44 §5(c) path. Likely **highest ROI / lowest cost**.

### Path C — Full-loading-screen deferral

**Concept:** Show a static "Loading semantic explorer..." overlay for the first 2 seconds. The overlay holds painting. When init is complete, the overlay fades out.

**Implementation sketch:**

- Add `LoadingOverlay.svelte` (already exists per W42) → mount always-active during init period
- Block LCP/FCP on init-completion event
- Engine runs in worker thread where possible
- DOM complexity hidden behind overlay

**Cost:** 2–4 days, mostly CSS/timing work.

**TBT projection:** **0 ms** (reload pain is "loading delay", not TBT penalty). Lighthouse Perf score ≈ 90 if loading counts as expected.

**Risk: LOW.** Cosmetic UX shift, no architectural change. But UX cost is real — users see "loading" before the 3D field appears.

---

## 3. Recommended Path

**Path B — Lazy-shell behind user gesture.**

Why:

- 3–5 day implementation window vs 2–3 weeks for SSR
- Doesn't risk breaking the bridge files / engine kernel architecture
- Bridges in `src/lib/engine/*-bridge.ts` survive intact (commits stay load-bearing-stable)
- TBT projection (50–150 ms) lands inside the 200 ms budget
- Preserves the W5 perf groundwork (RAF throttle + idle yields + worker offloads all become components of the post-gesture pipeline)

## 4. Tickets

### W6-T1 — Splash shell + gesture monitor (estimated 1 day)

- CSS-only `<canvas>` placeholder during gesture-gate period
- `<svelte:window>` gesture listener for `mousemove`, `keydown`, `pointerdown`, `wheel`, `touchstart`
- `engineReady` Svelte writable store → flipped to `true` after first gesture
- `<Canvas />` mounts lazily via `<Canvas mountWhen={engineReady()} />`
- Lighthouse-friendly: paint the splash, yield 5 ms intervals

### W6-T2 — `initEngine()` deferral wiring (estimated 2 days)

- `initEngine()` stays in main thread but called via `idleCallback` after gesture
- Worker continues computing mycelium data during splash period
- Add parity attribute `data-engine-state="deferred|ready"` for CSS/contract test surfaces

### W6-T3 — Bridge sanity verification (estimated 1 day)

- Verify all 41 bridges still fire correctly when init happens post-gesture
- Specifically: `state-bridge.ts`, `engine-bridge.ts`, `parity-attrs.svelte.ts`

- User feedback round: W6-T4 visual test with 5 internal testers
