## 🎯 W40 Goals

### T40-A: Lighthouse Baseline (Performance)

**Impact:** Establishes measurable performance reality before W41 dead-code elimination.
**Scope:** Run `lighthouse` against the production preview build and record the first meaningful paint, LCP, CLS, and INP.
**Approach:**

1. Serve `dist/svelte/` via `npx vite preview --port 4174`
2. Run `npx lighthouse http://127.0.0.1:4174/ --output=json --chrome-flags="--headless"`
3. Extract and record: LCP, CLS, INP, TTFB, Speed Index, Total Blocking Time
4. Compare against performance budget targets from `docs/performance-budget.md`
5. Save results to `docs/lighthouse-baseline-2026-06-18.json`

**Success criteria:**

- LCP < 2.5s mobile, < 1.5s desktop
- CLS < 0.1
- INP < 200ms
- Results committed and pushed

### T40-B: Deploy Script Verification

**Impact:** Ensures production deployment path works end-to-end after all W39 build changes.
**Scope:** Run the deploy script in dry-run mode, verify all expected artifacts are present, and confirm the production shell uses the updated lazy-loaded chunks.
**Approach:**

1. Read `deploy.sh` and `deploy.ps1` to understand the production deploy path
2. Run `deploy.ps1` (or `deploy.sh`) in dry-run/validate mode if available
3. Verify `dist/svelte/index.html` references the correct lazy-loaded chunk filenames
4. Verify `dist/svelte/assets/` contains all expected chunks (index, three, postprocessing, SearchResults, JourneyChrome)
5. Confirm no 404s when serving the production build locally

**Success criteria:**

- deploy script completes without errors
- All expected chunks present in `dist/svelte/assets/`
- `index.html` references all chunks correctly (no broken lazy-load paths)
- Production server serves the app without 404s

### T40-C: Visual Regression for Lazy-Loaded Components

**Impact:** Verifies that the lazy-load change in `343ccee` didn't break visual rendering of SearchResults and JourneyChrome.
**Scope:** Run visual regression tests for the surfaces that exercise SearchResults and JourneyChrome.
**Approach:**

1. Read `tests/visual-regression.test.ts` to understand the test matrix
2. Ensure the test runner triggers the lazy-loaded paths (search mode for SearchResults, focus/journey mode for JourneyChrome)
3. Run `npx playwright test tests/visual-regression.test.ts` for the affected surfaces
4. Compare against baselines; if any fail, investigate if it's a lazy-load timing issue or a real regression
5. Update baselines if the only change is lazy-load timing (acceptable)

**Success criteria:**

- Visual regression test for search state surfaces passes
- Visual regression test for focus/journey surfaces passes
- No regressions attributable to lazy-load timing (within 200ms threshold)

### T40-D: Performance Budget Review

**Impact:** Documents the actual achieved bundle sizes after all W39 optimizations.
**Scope:** Run `node scripts/check-bundle-size.mjs` and compare against `docs/performance-budget.md`.
**Approach:**

1. Run `npm run build:svelte` (fresh build)
2. Run `node scripts/check-bundle-size.mjs`
3. Record actual vs budget vs previous measured (from W40 audit)
4. Update `docs/performance-budget.md` "Current" column with new actuals
5. If any metric is >80% of budget, flag for W41 investigation

**Expected results (W39 actuals):**

```
JS (raw)    ~1,217 KB  (budget: 2,500 KB)  — ~1,283 KB slack
JS (gzip)     ~338 KB  (budget:   650 KB)  — ~312 KB slack
CSS (raw)      ~54 KB  (budget:    60 KB)  — ~6 KB slack
CSS (gzip)     ~10 KB  (budget:    12 KB)  — ~2 KB slack
```

**Success criteria:**

- Actual measurements recorded in performance budget document
- No metric >80% of budget ceiling
- Document updated and committed
