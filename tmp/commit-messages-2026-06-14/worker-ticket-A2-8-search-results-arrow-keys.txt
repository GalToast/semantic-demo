Implement arrow-key navigation within the search results list so keyboard users don't have to Tab through every result.

## Background

The a11y audit (2026-06-14) found:
- **A2-8 (HIGH):** When search results appear, each result is a separate Tab stop (`<button tabindex="0">`). With 10+ results, keyboard users must Tab through every result to reach the next landmark. The standard ARIA pattern for a list of results is roving tabindex with arrow-key navigation.

**WCAG:** 2.1.1 Keyboard (Level A)

**Evidence:**
```
#search-result-list: role="list", aria-label="Search result businesses"
Each result: <div role="listitem"> → <button tabindex="0">
No keydown handler on the list container
10 results = 10 Tab stops between search input and legend toggle
```

### Step 2: Implement arrow-key navigation

Follow the WAI-ARIA `listbox` pattern or `grid` pattern:

1. Only the active (focused) result should have `tabindex="0"`
2. All other results should have `tabindex="-1"`
3. Arrow key handlers on the list container (or each result):
   - ArrowDown: Move focus to next result
   - ArrowUp: Move focus to previous result
   - Home: Move focus to first result
   - End: Move focus to last result
4. When focus moves, update `tabindex` on the old and new results
5. Tab should EXIT the list to the next landmark (not move to the next result)

**Implementation approach:**
- Add `let activeResultIndex = $state(0)` to track which result has focus
- Add `tabindex={i === activeResultIndex ? 0 : -1}` to each result button
- Add `onkeydown` handler to the `#search-result-list` container
- On ArrowDown: increment `activeResultIndex`, focus the new result
- On ArrowUp: decrement `activeResultIndex`, focus the new result
- On Home: set `activeResultIndex = 0`, focus
- On End: set `activeResultIndex = last`, focus
- On Tab: let default behavior exit the list

### Step 3: Handle dynamic result count

The result list changes as the user types. When results update:
- Reset `activeResultIndex` to 0
- Focus the first result (if the list is visible)
